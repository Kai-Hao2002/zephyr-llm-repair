v3 把 v2 幾乎集中在單一 commit 的 151 筆案例，重做成分散在 個 base commit、每個 app 與注入檔只用一次的 筆案例。每一筆都經過重現、原始版本通過、標準答案修補三道自動驗證，並針對「agent 能否不靠理解程式碼就猜到答案」做了稽核與修正。

1. 為什麼重做資料集

  • 相關性過高：v2 的 151 筆有 個不同的 base commit，其中 141 筆在同一個 commit；只有 個不同的 test app，同一個 app 最多出現 6 次、22 個注入檔被重複使用。樣本彼此不獨立，統計檢定的有效樣本數會被高估。
  • 單一快照：結果只代表 Zephyr 某一天的狀態，外部效度弱。
  • 防改測試的保護不完整：v2 有 /151 筆有 target_test，其餘案例只靠「整個套件通過」判定。
  • QEMU 比例很低：v2 只有 筆在 QEMU 板子上。

注意：agent 之間沒有跨案例的資訊外洩（每筆獨立程序、無共享記憶），所以「答案被餵給 agent」不是問題本身；重做的理由是樣本相關性與外部效度。

為什麼日期從 2026-03-17 開始

用現有 Docker image（Zephyr SDK 1.0.1、模組為 2026-08 快照）實測：Zephyr 從 2026-03-17 起才要求 SDK 1.0；更早的 commit 在 CMake 設定階段就失敗（hal_silabs 模組的 fetcher 欄位 2026-02-24 前不認得、SDK 版本不符）。ARM（qemu_cortex_m3）因 cmsis_6 模組在 2026-05-07 改了目錄結構，只用該日以後的 commit。依使用者決定，範圍定為 2026-03-17～08，不另建 image。

3. 驗證流程

1 重現注入後 build/run 出現該類別預期的失敗；runtime 類必須失敗在 target_test。
→
2 原始版本不注入時 target_test 有 PASS（編譯期類別自動挑一個測試當防改測試的保護）。
→
3 標準答案走評測時完全相同的路徑（準備 workspace、受保護檔案、oracle）套用正確修補，必須判定修好。
→
4 穩定性runtime 案例注入版重跑 3 次、原始版重跑，每次結果都要一致。

環境與正式評測一致：模組用 image 快照、不跑 west update，建置指令相同。

被拒的 次嘗試

每次被拒都讀過 log 判斷原因，再換 commit、換板子、修正 target_test 或換 app 重試。

「原始版本失敗」包含：2026-01 commit 無法編譯、測試在新 commit 被改名（例如 test_sem_take_multiple → test_sys_sem_take_multiple）、上游測試本身在該 commit 失敗，以及下一節的 oracle 誤判（已修正後重驗通過）。

4. 稽核：agent 能不能不讀程式就猜到答案

發現處理結果
錯誤訊息直接露出答案：dts_break_phandle 把標籤改成 xxx_broken_ref，dtc 錯誤原文就是 undefined node label 'gnss_broken_ref'（v2 也有）改成自然的拼字錯誤（例如 gnns、pwn0）log 中 0 筆出現

案例 ID 含 offbyone 等字查 v2 共 453 次執行，ID 從未出現在 agent 看得到的 log無洩漏

5. 建置過程中修掉的評測基礎設施問題

這些問題會讓評分失真，都在 v3 正式評測前修正（v2 結果不受影響、維持凍結）：

  • log filter 吃掉 assertion：只要 log 有一條無害的 Kconfig 警告，執行期尾段就不輸出；v2 有 22 筆 runtime_crash 因此看不到失敗訊息。現在程式有開機就一定附上執行期尾段。
  • oracle 把預期內的 fault 判成 crash：QEMU 上的 userspace 測試會故意觸發 fault（ZEPHYR FATAL ERROR 後接 Caught system error -- reason N 1）。現在 fault 先記為待定，ztest 說是預期內的或該測試 PASS 就繼續。
  • oracle 把 log 內文的 "aborted" 判成主機端 abort（Enrollment aborted、aborted essential thread）。現在只認主機端的大寫 Aborted。
  • 上下文收集器不認相對路徑：Kconfig 警告寫 defined at subsys/fs/fcb/Kconfig:10，B3 因此在 v2 kconfig 上 0/20。現在三條 pipeline 都會收。
  • gemini-3.x 回傳內容區塊：response.content 是 list，Proposed/B2/B3 拿到 patch 就出錯；改用 .text。

6. 仍存在的限制

  • 函式名拼錯的 4 筆，gcc 會提示 did you mean '...'?（真實編譯器行為，可當成簡單組分析）。
  • 時間範圍只到 2026-03-17 之後（SDK 1.0 限制），ARM 只在 2026-05-07 之後；模組固定為快照，但抽樣顯示不影響結果。
  • 設定類（kconfig/dts/compound）在 QEMU 上只有 6 筆：附帶 QEMU overlay 的測試很少，coredump 類會刻意 crash，部分測試需要 tests.yaml 的額外設定。
  • 30 筆 runtime 的錯誤在測試程式本身，修的是測試碼而非 RTOS 程式碼。
  • 編譯期類別的 target_test 是自動挑的（優先選注入檔裡的測試），作用是防止改測試，不代表與錯誤直接相關。

7. 下一步
