ZEPHYR-EVAL · v2 評測分析

v2 失敗原因分析與檢索機制說明

Gemini 2.5 Pro 單模型 · 151 筆案例 × 4 條 pipeline · 結果凍結於 commit d06fd57 · 分析腳本 tools/failure_taxonomy.py

這份報告把四條 pipeline 每一筆沒修好的案例（共 筆）依 trajectory 自動分類，並逐類抽查實際內容。另外說明 RAG 的實際運作方式，以及目前已確認的幾項評測發現。

重點摘要

    1. 失敗原因分類

    分類規則

    每筆案例依序套用下列規則，第一條符合者即為主類別。「注入檔案」指資料集中被注入錯誤的檔案（compound 案例有兩個）。「受保護檔案」指 target_app 底下除了注入檔以外的測試與設定檔，評測端在每次建置前會把它們還原。

    類別判定方式（皆取自 iteration_log[].trajectory）

    附加標記不影響主類別：crash 訊號遺失（見第 3.1 節）、卡在 StaticCheck（同一案例 ≥2 次 cppcheck 失敗）、compound 只修一處、注入檔在／不在上下文（注入檔是否出現在初始 log 的絕對路徑、target_app 目錄、或任一輪的檢索結果中；B1 看不到任何檔案內容，一律記為不在）。

    各 pipeline 的失敗組成

    怎麼讀這張圖

    • B1 幾乎全部失敗在「看不到檔案」：41 筆路徑是編的（TargetFileNotFound），43 筆雖然猜對檔案，但是從記憶重寫整個檔案，編譯不過。
    • B3 的 筆失敗中，有 60 筆是「只改測試/設定，被還原」。B3 沒有檢索，看得到的只有 target_app 目錄和 log 裡的絕對路徑，所以它反覆修改 prj.conf 與測試程式。受保護檔案規則把這些修改全部擋掉。
    • B2 的定位失敗（改錯檔案 + 改測試被還原）共 58 筆，佔非 hang 失敗的 73%。BM25 直接拿整段 log 當查詢，查回來的常是無關檔案。
    • Proposed 的失敗以「改了別的檔案」為主（29 筆），其中 17 筆屬於第 3.1 節的 crash 訊號遺失案例。
    • 「改到注入檔案但仍失敗」在四條 pipeline 都只佔少數。v2 的主要瓶頸在定位，而不是「找到檔案後改不對」。

    抽查紀錄

    每一類至少讀了一筆完整 trajectory（patch 內容、套用錯誤、建置/執行 log），共 13 筆，確認自動分類與實際行為一致。

    Pipeline / 案例自動分類實際內容判定
    分類的限制：「改到注入檔案」只代表 patch 有動到那個檔案，不代表改在正確位置。例如 B3 的 inject_thread_priority_swap_semaphore 改了同一個檔案裡另一個執行緒的優先權。又如 Proposed 的 inject_api_substitute_sleep_yield_qemu_x86，動到注入檔的那一輪其實只改了無關內容。所以這兩類應解讀為「已定位到檔案層級」。

    2. RAG 怎麼運作

    v2 的 Proposed 只有 Hybrid RAG。Graph RAG 的圖譜快取在所有評測中都不存在，因此 Knowledge Expert 送給 Patch Expert 的圖譜 YAML 是空的。論文會把 Graph RAG 列為未來工作。

    Proposed：Analyzer 關鍵字 → BM25 + 語意重排 → RRF

    ANALYZER讀精簡後的錯誤 log，輸出 search_keywords。prompt 規定純 C 語法錯誤回傳空清單；遇到 undeclared 符號要推出子系統名稱（如 fcb）。
    →
    BM25關鍵字以空白串成查詢，對整棵 Zephyr 樹（.c .h .conf .dts .dtsi .overlay Kconfig*，約 3.7 萬檔）做 BM25，取分數 >0 的前 30 名。
    →
    語意重排30 個候選各取前 3000 字元做 embedding（v2：gemini-embedding-001），與查詢算 cosine 排序。
    →
    RRF 融合score = 1/(60+BM25名次) + 1/(60+語意名次)，取前 top_k = 8。
    →
    PATCH EXPERT上下文 = log 中的絕對路徑檔案 ∪ target_app 全部原始碼 ∪ 這 8 個檔案的全文（上限 30 萬字元），加上歷次嘗試摘要。

    每一輪失敗後都會回到 Analyzer 重新產生關鍵字，所以每一輪都會重新檢索。若 Analyzer 回傳空清單，該輪就完全不檢索。評測模式下，embedding 失敗會直接中止案例，不准退回純 BM25。

    3. 已確認的重要發現

    3.1 新發現：22 筆 runtime_crash 的錯誤訊號在 v2 中遺失

    這是評測基礎設施的問題，會影響 v2 runtime_crash 的數字，v3 開跑前必須修正。

    tools/log_filter.py 只在沒有任何規則命中時才輸出 log 尾端（[Fallback Raw Tail]），而 assertion 失敗的訊息就在尾端。2026-09-25 的修正（d0caa37）讓 filter 開始抓 Zephyr 格式的 Kconfig 警告。結果有 22 筆 runtime_crash 案例的 log 裡本來就有一條無害的 Kconfig 警告（14 筆是 MAX_THREAD_BYTES … USERSPACE (=n)，4 筆是 STDOUT_CONSOLE）。這條警告一命中，尾端就不再輸出，四條 pipeline 拿到的初始 log 和每一輪的 log 都只剩這條警告，真正的 Assertion failed at …/main.c:776 完全看不到。資料集裡當初記錄的 log 是有 assertion 的（舊版 filter），所以這是評測時才發生的。

    抽查的 B3 inject_runtime_sem_offbyone_baseline3 五輪都在修 MAX_THREAD_BYTES 警告（改 prj.conf 和板子 conf），每輪都被還原。那條警告在原始、未注入的版本中同樣存在，跟錯誤毫無關係。

    影響：先前的結論「runtime_crash 最難（Proposed 54%）」有很大一部分是這個問題造成的。排除這 22 筆後，Proposed 在 runtime_crash 是 39/56（70%），與其他類別相當。因此「錯誤訊號品質」對修復成功率的影響，在 v2 中其實有一組自然的對照：同一類錯誤，看得到 assertion 時約 41–70%，看不到時 5–14%。

    建議：log_filter 改成「若有 runtime 失敗特徵（Assertion failed、FAIL -、fatal error、Segmentation fault 等），一定附上尾端」。這是評測程式的修改，會先跟您確認再改；v3 一定要用修正後的版本。

    3.2 改測試的投機行為（spec gaming）

    在受保護檔案規則（4be1920）之前，agent 會把測試改成 ztest_test_skip()、改 assertion 或改 prj.conf 來「通過」。B3 在任一輪動過受保護檔案的 82 筆案例中，修好數從 21 降到 7（B3 整體 53.6% → 44.4%）。B1/B2 以離線重評處理（B1 4.0% → 2.6%，B2 一筆由修好變失敗）。規則上線後，B3 的 462 個迭代裡仍有 324 個（70%）有檔案被還原，代表 B3 的迭代大部分花在試圖修改規格上。

    3.3 B3 不再顯著優於 B2

    McNemar 檢定（只看兩邊結果不同的案例）：

    擋掉改測試之後，「有建置回饋、可迭代 5 次」的 B3 和「單次 + BM25」的 B2 幾乎打平（17 比 18）。也就是說，B3 舊結果中迭代帶來的優勢主要來自改規格。

    3.4 kconfig 類別上 B3 是 0/20

    機制：kconfig 案例的注入檔都在 target_app 之外（如 subsys/fs/fcb/Kconfig）。20 筆中有 13 筆的 log 其實寫出了這個路徑，但寫法是 Kconfig 的相對路徑格式 defined at subsys/fs/fcb/Kconfig:10。上下文收集器只認 /zephyrproject/zephyr/… 開頭的絕對路徑，所以 B3 從來沒看到注入檔，只能改 prj.conf，而 prj.conf 會被還原（15/20 歸為「只改測試/設定」）。B2 用整段 log 做 BM25，在 13/20 筆中第一次檢索就命中；Proposed 則是 18/20。這是「檢索比迭代重要」最清楚的一組證據。

    3.5 錯誤 log 有沒有注入檔路徑，對定位的影響

    以初始 log 是否出現注入檔的絕對路徑分組（排除 llm_hang）。「定位到」= 任一輪 patch 有成功套用到注入檔。

    有路徑時，四條 pipeline 都能 82–100% 定位到注入檔。沒有路徑時差異就出現了：B1 22%、B2/B3 約 48%、Proposed 70%。Proposed 相對於 baseline 的優勢幾乎全部來自「log 沒有路徑」的案例，而這正是檢索要解決的問題。注意只有 17–18 筆的 log 含注入檔的絕對路徑，大部分 c_syntax 的錯誤指向 ztest_test.h 之類被展開的巨集標頭。

    3.6 其他觀察

    • 路徑格式：Proposed 有 29 個迭代、B3 有 25 個、B2 有 9 個，因為把路徑寫成 <path> 導致 patch 套用失敗（PatchApplier 依決定維持嚴格，論文以「格式遵循」討論）。
    • StaticCheck 的副作用：Proposed 有 筆失敗案例出現 ≥2 次 cppcheck 失敗。例如 inject_compound_rtc_emul_kconfig_dts，cppcheck 對無關的 counter_stm32_rtc.c 報 #error Invalid RTC SRC，第 2–5 輪都花在處理這個誤報上。
    • llm_hang：B2 3、B3 7、Proposed 6 筆，各重試一次後仍無回應，依決定計為未修好。
